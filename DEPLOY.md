# Деплой «КАДР» — из Git сразу на стенд

Проект собирается в **один самодостаточный файл** `dist/index.html`
(весь JS и CSS заинлинены, внешний хост не нужен — только статика).
Поэтому подойдёт любой хостинг — включая обычный shared-хостинг (reg.ru и т.п.).

Ниже — способы для разных хостингов. **Для reg.ru смотрите первый раздел.**

---

## ★ reg.ru  (ваш случай: kadr-scr.ru)

### Почему была ошибка «module script MIME type»

reg.ru «Сайт из Git» выкладывает **корень той ветки, к которой подключён**.
Вы подключили ветку `main` — а в ней лежит **исходный код** (`src/main.tsx`),
а не сборка. reg.ru отдал исходный `index.html`, который ссылается на
`/src/main.tsx` → браузер получил его с пустым MIME-типом → ошибка.

**Правильно: подключить reg.ru к ветке `deploy`**, в которой лежит только
сборка. GitHub Actions создаёт и обновляет её автоматически при каждом пуше.

### ПУТЬ A — reg.ru «Сайт из Git» + ветка `deploy`  (рекомендуем)

1. Запушьте изменения в `main` (или запустите Actions → «Deploy to reg.ru» → Run workflow).
2. Дождитесь, пока workflow создаст/обновит ветку **`deploy`**
   (в репозитории появится ветка `deploy` с единственным файлом `index.html`).
3. В панели reg.ru: **Сайт из Git** → ваш репозиторий → в поле «Ветка»
   укажите **`deploy`** (вместо `main`/`master`). Сохраните.
4. Reg.ru выложит содержимое ветки `deploy` — и сайт заработает.
   Каждый следующий `git push` в `main` будет обновлять ветку `deploy`,
   а reg.ru — подхватывать её.

Ничего больше настраивать не нужно: ни FTP, ни секретов для этого пути не требуется.

### ПУТЬ B — FTP через GitHub Actions  (альтернатива)

На shared-хостинге нет «сборки по пушу», поэтому сборку делает GitHub Actions,
а готовый сайт загружается на хостинг по **FTP** при каждом пуше.
Всё уже настроено в `.github/workflows/deploy-regru.yml`.

**Шаг 1. Возьмите данные FTP в панели reg.ru**
Панель управления хостингом → раздел **«FTP»** (или «FTP-аккаунты») → данные доступа:
- адрес сервера (например `server290.hosting.reg.ru` или `ftp.kadr-scr.ru`);
- логин (в reg.ru обычно совпадает с доменом, вида `kadr-scr.ru`, или `uXXXXXX`);
- пароль.

Точную **папку сайта** видно там же (корень домена), у вас это `/www/kadr-scr.ru/`.

**Шаг 2. Добавьте секреты в GitHub**
Репозиторий → **Settings → Secrets and variables → Actions → New repository secret**.
Создайте четыре секрета:

| Имя секрета      | Значение                              |
| ---------------- | ------------------------------------- |
| `FTP_SERVER`     | `server290.hosting.reg.ru`            |
| `FTP_USERNAME`   | ваш логин FTP                          |
| `FTP_PASSWORD`   | ваш пароль FTP                         |
| `FTP_TARGET_DIR` | `/www/kadr-scr.ru/` (со слешем!)       |

**Шаг 3. Запустите деплой**
Запушьте изменения в `main`/`master` — либо запустите вручную:
**Actions → «Deploy to reg.ru (kadr-scr.ru)» → Run workflow**.

Через 1–2 минуты сайт будет на `https://kadr-scr.ru`. Каждый следующий
`git push` автоматически пересобирает и обновляет сайт.

> Если после загрузки сайт не открывается — проверьте `FTP_TARGET_DIR`:
> на reg.ru FTP-дом может отличаться от абсолютного пути. Посмотрите в панели
> reg.ru, в какую папку реально смотрит домен `kadr-scr.ru`, и укажите её.

## 0. Сначала: ключи БД (если подключаете Supabase)

Создайте файл `.env.production` в корне (рядом с `package.json`) по образцу
`.env.example` и впишите ключи из Supabase (Settings → API):

```
VITE_SUPABASE_URL=https://xxxx.supabase.co
VITE_SUPABASE_ANON_KEY=ваш-anon-ключ
```

Закоммитьте `.env.production` вместе с проектом — сборка подхватит его
автоматически на любой платформе. (anon-ключ публичный по дизайну Supabase,
доступ к данным защищён RLS-политиками, коммитить его безопасно.)

Если файл не создавать — сайт соберётся в локальном режиме (данные в
localStorage браузера), всё будет работать.

### Почему БД — это Supabase, а не MySQL на reg.ru

«КАДР» — это чистый фронтенд (один HTML-файл, без серверного кода). Браузер
**не может** подключиться к MySQL на хостинге напрямую — для этого нужен
серверный посредник (PHP/Node API на том же хостинге), что усложняет проект.

Supabase решает это без серверной части: это облачная PostgreSQL с готовой
аутентификацией, к которой сайт обращается прямо из браузера по HTTPS.
Схема БД и политики доступа уже лежат в `supabase/migrations/001_init.sql`.
Регистрация аккаунтов и хранение тестов включаются сразу после вставки ключей.

> Если принципиально нужна БД именно на reg.ru (MySQL) — это отдельная задача:
> придётся добавить PHP-API на хостинге. Скажите, и я подготовлю такой вариант.

## 1. Netlify  (рекомендуем — проще всего)

1. [app.netlify.com](https://app.netlify.com) → **Add new site → Import an existing project**.
2. Выберите ваш Git-репозиторий.
3. Netlify сам увидит `netlify.toml`: команда `npm run build`, публикация `dist`.
4. Нажмите **Deploy**. Через ~1 минуту сайт онлайн.

Дальше каждый `git push` в основную ветку автоматически пересобирает и
обновляет стенд.

## 2. Vercel

1. [vercel.com](https://vercel.com) → **Add New… → Project** → импорт репозитория.
2. Vercel подхватит `vercel.json` (сборка `npm run build`, папка `dist`).
3. **Deploy**.

Автодеплой на каждый пуш включён по умолчанию.

## 3. GitHub Pages  (если сайт на github.io)

Всё уже настроено в `.github/workflows/deploy.yml`:

1. Запушьте проект в ветку `main` (или `master`).
2. В репозитории: **Settings → Pages → Source → «GitHub Actions»**.
3. Во вкладке **Actions** дождитесь завершения «Deploy to GitHub Pages».
4. Сайт появится на `https://<логин>.github.io/<репо>/`.

Ключи БД для этого пути задаются в **Settings → Secrets and variables →
Actions** (секреты `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`) —
workflow уже прокидывает их в сборку. Либо просто закоммитьте `.env.production`.

---

## Проверка, что всё хорошо

- Откройте сайт. В тулбаре справа горит бейдж:
  **«БД: облако»** (зелёный) — подключён Supabase, или
  **«БД: локально»** — данные в браузере.
- Зарегистрируйтесь / войдите. Если бейдж «облако» — аккаунт создан в БД.

## Если сайт показывает ошибку или пустую страницу

Почти всегда причина одна: хостинг публикует **корень репозитория**, а не
папку `dist`. Убедитесь, что в настройках деплоя:

- Build command: `npm run build`
- Publish / Output directory: `dist`

Файлы `netlify.toml` / `vercel.json` / GitHub Actions уже содержат эти
значения, поэтому при импорте из Git ничего настраивать вручную не нужно.

# БД на reg.ru (MySQL + PHP-API)

Сайт — чистый фронтенд, поэтому к MySQL на хостинге он ходит через небольшой
**PHP-API** (папка `api/`). Он раскладывается на сервер вместе со сборкой и
работает на том же домене (`https://kadr-scr.ru/api/...`), поэтому CORS не
нужен. Режим включается переменной `VITE_BACKEND=regapi` (в workflow уже
прописано по умолчанию).

**Шаг 1. Создайте базу данных в reg.ru**
Панель → **«Базы данных»** → «Создать базу». Запомните: имя БД, пользователя и
пароль. Хост — почти всегда `localhost`.

**Шаг 2. Примените схему**
Там же → **phpMyAdmin** → выберите созданную БД → вкладка **SQL** → вставьте
содержимое файла [`mysql/schema.sql`](./mysql/schema.sql) → «Вперёд».
Создадутся таблицы `kadr_accounts`, `kadr_users`, `kadr_sessions`,
`kadr_account_state`.

**Шаг 3. Заполните реквизиты**
Откройте [`api/config.php`](./api/config.php) и впишите `db_name`, `db_user`,
`db_pass` из шага 1. Закоммитьте файл (репозиторий держите **приватным** —
пароль БД лежит в этом файле, но он попадает на сервер при каждом деплое и
самовосстанавливается).

**Шаг 4. Запушьте**
```bash
git add . && git commit -m "db: подключаем MySQL на reg.ru" && git push
```
Workflow соберёт фронтенд с `VITE_BACKEND=regapi`, скопирует `api/` в `dist/`
и выложит всё на сервер (ветка `deploy` / FTP).

**Проверка:** откройте сайт, зарегистрируйтесь. Данные должны сохраняться между
браузерами/устройствами. Быстрая диагностика API:
`https://kadr-scr.ru/api/state.php` — без токена вернёт `{"ok":false,...401}`
(это норма, значит PHP и БД отвечают).

## Важные нюансы

- **Регистрация и вход** обрабатываются PHP: пароль хранится только как
  bcrypt-хеш (`password_hash`), сессия — случайный токен с временем жизни.
- **Доступ к данным** у каждого пользователя только к своему рабочему месту
  (все запросы проверяют токен и `account_id`).
- Служебные файлы `config.php`, `db.php`, `common.php` закрыты от прямого
  доступа по URL (`api/.htaccess`).
- Если нужно переключиться на Supabase — задайте его секреты: он имеет
  приоритет над regapi.

## Структура файлов БД

```
api/                  # PHP-API (раскладывается в dist/api/ при сборке)
  config.php          # реквизиты MySQL — ЗАПОЛНИТЬ
  db.php, common.php  # подключение и помощники
  register/login/restore/logout/state/users.php  # эндпоинты
  .htaccess           # закрывает служебные файлы
mysql/schema.sql      # схема — применить в phpMyAdmin
src/backend/regapi.ts # фронтенд-адаптер (режим regapi)
```
